How the Frame runs PC games, and where it breaks

The Steam Frame is an ARM64 Linux headset. Nothing in your Windows library runs on it natively. Every "standalone" launch of a PC game goes through a long chain, and each guide on this site is one link in that chain failing.

The chain

A Frame-native game from the Steam store is an Android APK (Red Matter, Pavlov Shack, Pistol Whip and so on ship this way). Everything else is the Windows x86-64 build, started like this:

Steam client (ARM64)
  → steam-launch-wrapper → reaper
    → Steam Linux Runtime 4 (pressure-vessel container)
      → FEX  (translates x86-64 code to ARM64 on the fly)
        → Proton 11.0 (ARM64) or Proton Experimental (ARM64)
          → Wine, with DXVK turning Direct3D into Vulkan on the Adreno 750 (Turnip driver)
            → the game's Windows .exe
VR:  OpenVR games  → Proton's vrclient bridge → SteamVR on the headset
     OpenXR games  → wineopenxr → SteamVR's OpenXR runtime

Since 2026-10-20 there is a fifth path: ports whose source is public are compiled on the headset itself and talk to SteamVR's ARM64 OpenXR or OpenVR libraries directly, with no container, FEX or Proton in between. That is the Native ARM64 builds page.

Logs for each layer land in ~/.local/share/Steam/logs on the headset. The game's "C: drive" is a Proton prefix at ~/.local/share/Steam/steamapps/compatdata/<appid>/pfx.

What every fix here has in common

  • Nothing outside your home folder changes. SteamOS stays read-only; the fixes are launch options, small scripts in /home/steamos, or files inside a game folder or its prefix. Each guide ends with how to undo it.
  • You need SSH to the headset. Turn on Developer Mode (Steam Settings → System → Enable Developer Mode), set a user password in the new Developer section, then from a PC run ssh steamos@frame.local. The Toolbox page has the rest.
  • Launch options are the main lever. On the headset: Library → game → Properties → Launch Options. %command% stands for the whole launch command Steam would have run.
  • Wrapper scripts, not inline tricks. Steam strips backslashes from launch options and several fixes need to swap the executable Steam starts. So the pattern is a tiny bash script in the home folder that receives the full command as arguments, edits one of them, and runs the result:
#!/bin/bash
a=("$@")                       # everything Steam was about to run
for i in "${!a[@]}"; do
  case "${a[$i]}" in
    */Launcher.exe) a[$i]="${a[$i]%/*}/Real/Game.exe" ;;   # swap one argument
  esac
done
exec "${a[@]}"                 # run the edited command

Launch option: /home/steamos/scriptname %command%. The Contractors, Halo and FighterZ guides are all this shape.

Toolbox and commands

The handful of commands the guides lean on. All of them run from a PC against the headset over SSH, as the steamos user.

Get in

  1. On the Frame: Steam Settings → System → Enable Developer Mode. A Developer section appears; at its bottom choose Set User Password.
  2. On Windows, in PowerShell: ssh steamos@frame.local. Type yes the first time, then the password. If frame.local does not resolve, use the IP from Settings → Internet.
  3. Optional, saves typing the password: ssh-keygen -t ed25519 -f $env:USERPROFILE\.ssh\frame_ed25519 -N "", append the .pub to ~/.ssh/authorized_keys on the Frame, and add a Host frame block to ~/.ssh/config. This headset is set up that way, so the guides write ssh frame.
Developer Mode exposes SSH and ADB to everyone on your network. Turn it off when you are done for the day.

When a game hangs and Stop does not clean up

On this headset, Stop in the Steam menu (and the client's TerminateApp) killed the launch wrapper but left the Wine processes alive inside the runtime container. The old wineserver then held the prefix lock and the next launch sat forever in wineserver -w. Kill the whole launch through its systemd scope instead:

ssh frame 'systemctl --user list-units --all "app-steam-app963930*"'
ssh frame 'systemctl --user kill --signal=KILL app-steam-app963930-<pid>.scope'
# then confirm nothing is left for that prefix
ssh frame 'pgrep -x wineserver; for d in /proc/[0-9]*; do tr "\0" "\n" < $d/environ 2>/dev/null | grep -q compatdata/963930 && echo stale ${d#/proc/}; done'
Wine processes show their command line with Windows paths (S:\steamapps\common\...\Game.exe). A pkill -f pattern with forward slashes will not match them, and a pattern typed into an SSH one-liner will match the shell that is running it. Put kills in a script file.

Talking to the Steam client directly

The Steam client on the Frame runs with its Chromium debug port open on 127.0.0.1:8080 (on the headset only). A small Python WebSocket client can evaluate JavaScript in its SharedJSContext, which is how launch options and compat tools were set from the PC without touching the headset UI. ~/PCVR/bin/steam_eval.py does exactly that:

ssh frame 'python3 ~/PCVR/bin/steam_eval.py "SteamClient.Apps.SetAppLaunchOptions(963930, \"/home/steamos/contractors %command%\")"'
ssh frame 'python3 ~/PCVR/bin/steam_eval.py "SteamClient.Apps.RunGame(\"963930\", \"\", -1, 100)"'
ssh frame 'python3 ~/PCVR/bin/steam_eval.py "SteamClient.Apps.TerminateApp(963930, false)"'

Useful read-only calls: appDetailsStore.GetAppDetails(id).strLaunchOptions, .strCompatToolName, SteamClient.Apps.GetLaunchOptionsForApp(id).

The VR session: restarting it, and what never to do

# Restart SteamVR and the whole VR session (drops the wearer to the Frame's home; ask first)
ssh frame "systemctl --user restart gamescope-session.target"

# Stop a sideloaded game cleanly by its shortcut appid
ssh frame "python3 ~/PCVR/bin/steam_shortcuts.py stop 3173477041"
Never pkill -9 vrserver. It leaves the compositor and the headset driver in a state only a full session restart clears, and the restart drops whoever is wearing the headset.
Any frame-timing measurement is only valid while someone is wearing the headset. When the Frame is asleep SteamVR sets shouldRender off, native games stop rendering the eyes and time only their desktop mirror, and every number comes out wrong. See Quake VR: Unleashed for how that cost a morning.
PowerShell on the PC mangles quotes, $, [] and | inside ssh frame "..." one-liners. Anything longer than a word goes in a script file, scp'd over and run with bash.

What you see

  • Press Play. Steam shows the game as running and the headset stays in SteamVR Home. Nothing ever appears.
  • After a minute or so you press Stop. Every attempt since 2 October looked like this.
  • Reinstalling does nothing. Switching Proton versions does nothing.

Why it breaks on the Frame

Steam offers four depots for Contractors and all of them are Windows x86-64; there is no Frame-native build. The launch entry starts Contractors.exe in the game's root folder, a 147 KB file. That is Unreal Engine's BootstrapPackagedGame: it checks that the Visual C++ runtime and DirectX are installed, then starts the real executable, Contractors_UE4_22/Binaries/Win64/Contractors_UE4_22_Steam-Win64-Shipping.exe.

The check fails here. Steam's install script for this game installs the 2015 runtime (it is what the app's shared depots list), which writes version 14.0.24215 into the prefix registry. The bootstrapper was built with a newer toolchain and reads Major, Minor, Bld and Rbld from HKLM\SOFTWARE\Microsoft\VisualStudio\14.0\VC\Runtimes\x64, decides 14.0 is too old, then looks for the installer it would normally offer to run, Engine\Extras\Redist\en-us\UE4PrereqSetup_x64.exe. The Steam build does not ship that file. So it shows a Yes/No message box ("The following component(s) are required to run this program ... Would you like to install them now?") on the Wine desktop and waits. In VR that desktop is invisible. The game never starts.

The registry key, the two runtime files the bootstrapper also tests for (msvcp140_2.dll, vcruntime140_1.dll) and xinput1_3.dll all exist in the prefix. Only the version comparison fails.

The fix

Skip the bootstrapper and start the shipping executable directly. The wrapper takes the launch command Steam built and swaps one argument.

  1. Create /home/steamos/contractors on the headset with this content: 
    #!/bin/bash
# Steam hands this script its full launch command as arguments.
# Contractors.exe is Unreal's "BootstrapPackagedGame" launcher: it checks the
# VC++ / DirectX redistributables and, when it is not satisfied, pops a Yes/No
# dialog that is invisible in VR, so the real game never starts on the Frame.
# Skip the bootstrapper and run the shipping executable directly.
a=("$@")
for i in "${!a[@]}"; do
  case "${a[$i]}" in
    */ContractorsVR/Contractors.exe)
      a[$i]="${a[$i]%/*}/Contractors_UE4_22/Binaries/Win64/Contractors_UE4_22_Steam-Win64-Shipping.exe"
      ;;
  esac
done
exec "${a[@]}"
    From a PC, after saving it as contractors: scp contractors steamos@frame.local:~/ && ssh steamos@frame.local chmod 755 contractors
  2. In the headset's library: Contractors VR → Properties → Launch Options: 
    /home/steamos/contractors %command%
  3. Launch. The game's own -hmd=steamvr argument is kept, so it comes up in VR as before.

Caveats

  • First run downloads your mod.io maps. Contractors pulls every community map you are subscribed to into Contractors_UE4_22/ApeModio/. On this headset that was 1.4 GB in the first two minutes, which pushed the internal drive from 2.6 GB free to under 1 GB. Keep space in reserve or unsubscribe from maps you do not use.
  • No anti-cheat is involved (the SCUE4 plugin the game bundles is an in-process scanner and loads fine), so online play is not blocked by this fix.
  • Nothing about the game's data changes; this only changes which executable Steam starts.
  • Untested alternative: installing the Visual C++ 2022 redistributable into the prefix would make the stock bootstrapper pass, but a prefix reset or a future Steam install script run would undo it. The launch option survives both.

What you see

Why it breaks on the Frame

1. The prefix is poisoned by Easy Anti-Cheat's installer

MCC's Steam install script runs easyanticheat\easyanticheat_eos_setup.exe install inside the prefix. That installer bundles a Visual C++ 2017 redistributable and writes Microsoft's Windows x86-64 C runtime DLLs into windows/system32 (and i386 ones into syswow64): ucrtbase.dll, msvcp140.dll, vcruntime140.dll, concrt140.dll, vccorlib140.dll, vcomp140.dll, mfc140*.dll and about forty api-ms-win-*.dll stubs. On a PC that is harmless. On the Frame, Proton's own system DLLs are ARM64 builds, and Wine's own boot process now tries to load Microsoft's x86-64 ucrtbase.dll from inside ARM64 code:

err:module:import_dll Loading library ucrtbase.dll (which is needed by L"C:\windows\system32\sechost.dll") failed (error c000007b)
err:module:... Importing dlls for L"C:\windows\system32\wineboot.exe" failed, status c0000135
Unhandled exception code c000001d   (in libarm64ecfex.dll)

Wine cannot even boot the prefix, so every launch dies in three seconds.

2. The VR mod crashes inside Direct3D

Once the prefix was repaired the mod injected, reported "headset found on runtime SteamVR/OpenXR 2.18.2", printed "D3D11 hooks installed" and then died with exception C000001D (illegal instruction) at an address inside d3d11.dll. Proton ARM64's DXVK is a native ARM64 library; the mod's MinHook writes x86-64 trampolines into it. The fix is to give the game an x86-64 DXVK, which Proton also ships.

The fix

Step 1: repair the prefix

Save this as repair-mcc-prefix.sh on the PC and run it with ssh frame 'bash -s' < repair-mcc-prefix.sh. It moves every foreign runtime DLL into a backup folder inside the prefix and copies Proton's own versions back. On this headset the result was restored=12 backed-up-only=104.

#!/bin/bash
# repair-mcc-prefix.sh
#
# Halo MCC (Steam app 976730) on Steam Frame: the Easy Anti-Cheat setup that MCC's
# install script ran carried a bundled Visual C++ 2017 redistributable, which
# overwrote Proton's ARM64 (system32) and 32-bit (syswow64) C runtime DLLs with
# x86-64 / i386 Microsoft copies. Proton's own wineboot.exe then fails to load
# ucrtbase.dll (error c000007b) and the game never starts.
#
# This restores Proton's copies. Every foreign file is MOVED to a backup folder
# inside the prefix, never deleted, so the change can be rolled back.
set -u
P="$HOME/.local/share/Steam/steamapps/compatdata/976730"
PR="$HOME/.local/share/Steam/steamapps/common/Proton Experimental (ARM64)"

if pgrep -f "MCC-Win64-Shipping|compatdata/976730" >/dev/null; then
  echo "ABORT: MCC or its Proton prefix is in use. Close the game first."; exit 1
fi
[ -d "$P/pfx/drive_c/windows/system32" ] || { echo "ABORT: prefix not found at $P"; exit 1; }
[ -d "$PR/files/lib/wine/aarch64-windows" ] || { echo "ABORT: Proton Experimental (ARM64) not found"; exit 1; }

B="$P/polluted-backup-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$B/system32" "$B/syswow64"
restored=0; backed=0
for d in system32 syswow64; do
  src=aarch64-windows; [ "$d" = syswow64 ] && src=i386-windows
  cd "$P/pfx/drive_c/windows/$d" || exit 1
  for f in ucrtbase.dll msvcp140.dll vcruntime140.dll concrt140.dll vccorlib140.dll vcomp140.dll mfc140*.dll api-ms-win-*.dll; do
    [ -f "$f" ] || continue                          # unmatched glob
    [ -L "$f" ] && continue                          # Proton symlink, leave it
    grep -q -a "Wine builtin DLL" "$f" && continue   # already Proton's copy
    mv "$f" "$B/$d/" || exit 1
    if [ -e "$PR/files/lib/wine/$src/$f" ]; then
      cp "$PR/files/lib/wine/$src/$f" "$f"; restored=$((restored+1))
    elif [ -e "$PR/files/share/default_pfx_arm64/drive_c/windows/$d/$f" ]; then
      cp -L "$PR/files/share/default_pfx_arm64/drive_c/windows/$d/$f" "$f"; restored=$((restored+1))
    else
      backed=$((backed+1))   # no Proton equivalent (mfc140*, api-ms-*): backed up only
    fi
  done
done
echo "restored=$restored  backed-up-only=$backed"
echo "backup folder: $B"
echo
echo "verify (want builtin=1 and Aarch64 in system32, Intel 80386 in syswow64):"
for d in system32 syswow64; do
  for f in ucrtbase.dll msvcp140.dll vcruntime140.dll concrt140.dll; do
    p="$P/pfx/drive_c/windows/$d/$f"
    printf "  %s/%-18s builtin=%s %s\n" "$d" "$f" "$(grep -c -a 'Wine builtin DLL' "$p")" "$(file -b "$p" | grep -o -E 'x86-64|Aarch64|Intel 80386')"
  done
done

Step 4: the wrapper and launch option

Save as /home/steamos/mcc (the mod folder also keeps a copy as mcc-launch.sh):

# Normal entry (mcclauncher.exe, EAC) -> run the game directly with -no-eac: FLAT, no anti-cheat.
# "Anti-Cheat Disabled" entry        -> start the VR mod launcher instead: VR.
# EAC is never started on the Frame: its bootstrapper can reinstall the VC++ runtime that
# broke the Proton prefix, and EAC does not work under FEX anyway.
# frame_quadfix layer (VR): Touch-profile filter + View/D-pad bridge; quads keep their eye visibility but get
# normalised orientations (the F1 panel in stereo gameplay was rejected as XR_ERROR_POSE_INVALID otherwise).
export FRAMEXR_QUAD=norm
# Proton/FEX logging traces every exception and slows the game; MCC_LOG=1 turns it back on.
[ "$MCC_LOG" = 1 ] || unset PROTON_LOG
a=("$@")
vr=0
for i in "${!a[@]}"; do
  case "${a[$i],,}" in
    *mcc-win64-shipping.exe)
      root="${a[$i]%/*/*/*/*}"
      a[$i]="$root/Halo_MCC_VR/HaloMCCVRLauncher.exe"
      vr=1

What you see

Why it breaks on the Frame

Snapshot VR's Foveated Rendering feature asks the runtime for XR_FB_foveation, XR_FB_foveation_configuration and XR_FB_foveation_vulkan, but not XR_FB_swapchain_update_state, which the OpenXR spec lists as a required dependency of XR_FB_foveation. SteamVR on the Frame checks that dependency and refuses to create the OpenXR instance. Unity then gives up on VR and runs flat.

xrCreateInstance: Application is requesting the following extensions:
    XR_EXT_user_presence, XR_FB_foveation, XR_FB_foveation_configuration, XR_FB_foveation_vulkan,
    XR_KHR_vulkan_enable, XR_KHR_composition_layer_depth, XR_KHR_visibility_mask, XR_META_performance_metrics
[Error] xrCreateInstance error: attempted to enable XR_FB_foveation without enabling required XR_FB_swapchain_update_state

A PC is fine because SteamVR on Windows does not advertise XR_FB_foveation, so Unity never asks for it. The Frame advertises it because the headset supports foveated rendering. Games built with Unity OpenXR 1.15 or newer request the dependency correctly (WRATH: Aeon of Ruin VR, built with 1.17, runs fine).

The fix is a tiny implicit OpenXR API layer. It sits between the game and SteamVR and, only when a game enables XR_FB_foveation without XR_FB_swapchain_update_state, appends the missing name. Every other call passes straight through.

The fix

Needs SSH, gcc on the Frame (or a prebuilt libXrApiLayer_fovfix.so copied to the home folder first; the one built from this source has SHA-256 cf1cf35709303eab38259ff06e0755f3b6e2ee72be12aa4ab75e04a255833698), and the game installed. Nothing needs root; everything lives under the steamos home folder and survives SteamOS updates.

  1. Save the script below as install-snapshotvr-fovfix.sh on the PC.
  2. scp install-snapshotvr-fovfix.sh steamos@frame.local:~/ (and the prebuilt .so too, if you are not compiling).
  3. Run it on the Frame; the sed only strips Windows line endings: 
    ssh steamos@frame.local "sed -i 's/\r$//' install-snapshotvr-fovfix.sh && bash install-snapshotvr-fovfix.sh"
    Expected output: Compiling layer with gcc... (or installing prebuilt), Installed: listing two files, Done.
  4. Quit Snapshot VR if it is running and launch it again. It comes up in VR.

#

static XrResult fovfix_xrGetInstanceProcAddr(XrInstance instance, const char *name, PFN_xrVoidFunction *fn)
{

        if (fn) *fn = NULL;
        return XR_ERROR_FUNCTION_UNSUPPORTED;

static XrResult fovfix_xrCreateApiLayerInstance(const XrInstanceCreateInfo *info,
                                                const XrApiLayerCreateInfo *layerInfo,
                                                XrInstance *instance)
{
    if (!info || !layerInfo || !layerInfo->nextInfo || !layerInfo->nextInfo->nextCreateApiLayerInstance)
        return XR_ERROR_INITIALIZATION_FAILED;

    const XrApiLayerNextInfo *ni = layerInfo->nextInfo;
    next_gipa = ni->nextGetInstanceProcAddr;

    XrApiLayerCreateInfo next_layer_info = *layerInfo;
    next_layer_info.nextInfo = ni->next;

    int has_fov = 0, has_dep = 0;
    for (uint32_t i = 0; i < info->enabledExtensionCount; i++) {
        const char *e = info->enabledExtensionNames[i];
        if (!e) continue;
        if (!strcmp(e, EXT_FOV)) has_fov = 1;
        if (!strcmp(e, EXT_DEP)) has_dep = 1;
    }

    if (!(has_fov && !has_dep))
        return ni->nextCreateApiLayerInstance(info, &next_layer_info, instance);

    const char *mode = getenv("XR_FOVFIX_MODE");
    int strip = (mode && !strcmp(mode, "strip"));

    const char **names = calloc((size_t)info->enabledExtensionCount + 1, sizeof(char *));
    if (!names) return XR_ERROR_OUT_OF_MEMORY;
    uint32_t n = 0;
    for (uint32_t i = 0; i < info->enabledExtensionCount; i++) {
        const char *e = info->enabledExtensionNames[i];
        if (strip && e && (!strncmp(e, "XR_FB_foveation", 15) || !strcmp(e, "XR_META_foveation_eye_tracked")))
            continue;
        names[n++] = e;
    }
    if (!strip) names[n++] = EXT_DEP;

    XrInstanceCreateInfo mod = *info;
    mod.enabledExtensionCount = n;
    mod.enabledExtensionNames = names;

    logmsg("app '%s' (engine '%s') enabled %s without %s -> %s",

Why it breaks on the Frame

The game then takes about 55 seconds to initialise under FEX (the 184 MB exe has to be translated), creates its 1280x720 Unreal window and a working DXVK swapchain, and one second later initialises its own anti-cheat client. With file tracing on, that step reads:

Things that were tried and made no difference, which is how the cause was narrowed down: windowed mode, Proton Experimental (ARM64), bypassing the launcher with a wrapper (with and without -eac-nop-loaded), and renaming EasyAntiCheat_x64.dll so the client could not load at all. On Windows, the Unverum mod manager runs this game without anti-cheat for offline modded play. That was tried here too. The renamed copy still loads EasyAntiCheat_x64.dll, the DLL still fails for lack of its Wine module, and the game still quits at the same point. Older Unverum releases shipped byte-patched executables for this game, which is the only remaining route and was not pursued.

Native ARM64 builds: when Proton cannot do the VR part

Five of the ports on this site do not go through Proton at all. Their source was cloned onto the headset and compiled for ARM64 Linux, talking to SteamVR directly. This page is the shared recipe; each game's page has only what differed.

Toolchain on the Frame
gcc 15.1, clang 19.1, cmake, ninja, make, SDL2 2.30.2, OpenXR headers 1.1.40, OpenVR in /usr/lib
OpenXR runtime
/opt/steamvr/bin/linuxarm64/libopenxr_loader.so (SteamVR/OpenXR 2.18.2)
GPU path
OpenGL 4.6 through zink on Turnip (Adreno 750), 72 Hz, 1728x1728 per eye recommended
Built this way
Quake (Team Beef), Quake II, Quake III, Quake VR: Unleashed, RTCW (RealRTCW XR), Doom 3 BFG VR, AvP VR

When you need it

  • The game renders with OpenGL and talks OpenXR. Proton's wineopenxr bridges Direct3D 11, Direct3D 12 and Vulkan sessions only. An OpenGL game dies at wine_xrCreateSession Unhandled graphics binding type: 1000023000. All three Quake ports and AvP are this case.
  • The game is a sideloaded x86-64 OpenXR build. The Steam Linux Runtime container imports only SteamVR's ARM64 runtime, so VR never attaches (the old Quake dead end).
  • OpenGL plus OpenVR works under Proton (GZDoom VR), except for IVRCompositor::SetSkyboxOverride, which the ARM64 bridge asserts on. Doom 3 BFG VR was rebuilt natively for exactly that one call.

Everything else, Direct3D games and Unity or Unreal VR mods, stays on the Proton route; see the other pages.

The recipe

  1. Clone on the headset, shallow: git clone --depth 1 <repo> ~/PCVR/<Port>/src. The internal drive is nearly full; use --depth 1, sparse checkouts for big repos, and hard links (ln) for game data instead of copies.
  2. Port the OpenXR graphics binding. Windows ports create the session with XrGraphicsBindingOpenGLWin32KHR (wglGetCurrentDC / wglGetCurrentContext). On Linux the same four lines become the Xlib binding; everything else in the VR code is usually portable already: 
    #define XR_USE_PLATFORM_XLIB 1          /* instead of XR_USE_PLATFORM_WIN32 */
#include <X11/Xlib.h>
#include <GL/glx.h>
...
XrGraphicsBindingOpenGLXlibKHR binding = {0};
binding.type        = XR_TYPE_GRAPHICS_BINDING_OPENGL_XLIB_KHR;
binding.xDisplay    = glXGetCurrentDisplay();
binding.glxDrawable = glXGetCurrentDrawable();
binding.glxContext  = glXGetCurrentContext();
    GL entry points come from glXGetProcAddressARB or SDL_GL_GetProcAddress instead of wglGetProcAddress. Keep the patch as a small idempotent Python script next to the clone (q2_port.py, q1pc_port.py, d3_patch_arm.py) so it survives a git pull.
  3. Link SteamVR's loader by full path. /usr/lib/libopenxr_loader.a is a 14 KB stub, and sdl2-config --libs puts -L/usr/lib first, so -lopenxr_loader silently links the stub and every xr* symbol comes back undefined. Pass /opt/steamvr/bin/linuxarm64/libopenxr_loader.so -Wl,-rpath,/opt/steamvr/bin/linuxarm64 instead. The system headers are OpenXR 1.1.40; a project that needs newer extensions brings its own headers (Quake VR: Unleashed needs 1.1.63 for body tracking).
  4. MSVC habits. A plain inline function used from another file links on MSVC and fails on GNU C99 (no external definition; RTCW's game module). Stale generated prototypes and implicit int become hard errors with GCC 15; -Wno-error=incompatible-pointer-types and friends buy time, real mismatches still need fixing. After every build, check the modules: ldd -r x.so | grep 'undefined symbol'.
  5. x86 leftovers. Drop -msse/-msse2 flags, guard SSE intrinsics as x86-only, or route them through SIMDe with SIMDE_ENABLE_NATIVE_ALIASES when the code depends on them (Quake VR's audio and ambient-occlusion bake). GCC 15 defaults to C23, where true/false are keywords: add -std=gnu99 or -std=gnu17; old engines also want -fcommon and -fpermissive. ARM's char is unsigned: -fsigned-char cured garbled text in Doom 3.
  6. Modules. A game that loads its renderer or game logic as .so files needs -Wl,-Bsymbolic on those modules. Windows DLLs never see the executable's symbols; ELF does, and Quake II's renderer bound to the executable's copy of R_SetMode and spun forever.
  7. The launch wrapper. Every port starts through a two-line script, because Steam's game session sets things the native build must undo: 
    #!/bin/bash
cd "$(dirname "$0")"
export SDL_VIDEODRIVER=x11                                   # the OpenXR binding is GLX, not Wayland
unset MESA_GL_VERSION_OVERRIDE MESA_GLSL_VERSION_OVERRIDE   # Steam caps Mesa at GL 4.3; a 4.6 core context fails with GLXBadFBConfig
exec stdbuf -oL -eL ./game "$@" > game-last.log 2>&1    # line-buffered log beside the binary
  8. Add it to Steam as a native shortcut (no compat tool) with the VR flag, and give it red-labelled art: 
    ssh frame 'python3 ~/PCVR/bin/steam_shortcuts.py add "Quake II VR" /home/steamos/PCVR/Quake2VR-game/q2vr-run.sh /home/steamos/PCVR/Quake2VR-game'

zink: what OpenGL-on-Vulkan does differently

  • Finish before you release. SteamVR can read an eye image before zink has finished drawing it. The symptom is a jittering view, worst when you turn your head; a menu panel that is drawn later in the frame looks fine. The fix is glFinish() right before xrReleaseSwapchainImage for every eye. glFlush() is not enough. The cost is pipelining, so GPU time has to stay well under 13.9 ms. Quake II needed it for the right eye only (the left was flushed by the mirror swap); Quake VR: Unleashed needs it for both.
  • Bindless textures crash the driver inside libgallium while compiling the world shader (Quake VR: Unleashed). Turn GL_ARB_bindless_texture off even though it is advertised.
  • Bloom paints the eyes black in Quake VR: Unleashed, with the game otherwise at 72 Hz. Not traced yet; bloom is off.
  • Clip control (GL_ARB_clip_control, reversed Z) is advertised; Quake VR's shadows need it and work. A GL 4.3 override from Steam's session is what breaks core-context creation, not zink.

Performance, and how to measure it

  • The compositor shares the Adreno 750 with the game. Budget about 10 ms of GPU per frame for the game at 72 Hz. Below roughly 20 fps SteamVR blanks the world while still showing the game's menu panels: a "black world with sound" is almost always a frame-rate problem, not a rendering bug.
  • Measure only with the headset awake and worn. Asleep, SteamVR sets shouldRender off, native games skip the eyes and render only their mirror window, and every number is for the wrong thing.
  • In-game GPU timestamp profilers are unreliable per pass on this tile-based GPU: the first scope absorbs the whole render pass. Trust frame totals, and bisect features with cumulative console-command sweeps.
  • Resolution is the lever that always works: Quake VR: Unleashed costs about 4.6 ms per megapixel plus 4.5 ms fixed, so 72 Hz holds at about 650x650 an eye. Dynamic resolution helps only if its floor is low enough to reach a frame it can finish.

Rules that came out of the corrections

  • Grips never carry core actions. They fire from simply holding the controller. Steam's stock Frame layout presses a grip at 10% squeeze, which blocked attacking in Heretic and Hexen and dropped weapons elsewhere.   • Stick directions as buttons need hysteresis. Press at 60–75%, release at 30%, or snap turn and weapon switching re-fire while the stick is held. Doom 3's binding does this in the game patch; the SteamVR bindings do it with the 75% deadzone.
  • Pause is always the menu button, with no hidden gestures. Where a mod lacks a pause action, add one (the DUSK plugin maps menu to the pad's Start; Doom 3's patch sends Escape).
  • Recenter is always the right stick click. If the mod insists on a combination, keep that working too.
  • A selects and B goes back in menus wherever the mod has separate menu actions.
  • Head-oriented movement wherever we control it (the DUSK plugin, QuakeQuest's own option).

Why native

The Windows release is OpenGL plus OpenXR, the combination Proton on the Frame cannot bridge (Native ARM64 builds). The port's VR layer turned out to be almost entirely portable: the only Windows-specific code was the platform define in vr_tbxr.h and four lines creating the session with wglGetCurrentDC / wglGetCurrentContext in vr_xr.c. Everything else already goes through SDL. The game-change relaunch (Host_RelaunchGame_f) is Windows-only, so expansions are launched with -game instead of from the menu.

What the build script passes to DarkPlaces' own makefile, and why:

make sdl-release -j6 DP_MAKE_TARGET=linux DP_SOUND_API=SDL SDL_CONFIG=sdl2-config \
  CFLAGS_EXTRA="-std=gnu99 -fcommon -Wno-error" CFLAGS_SSE= CFLAGS_SSE2= \
  LDFLAGS_LINUXSDL='$(LDFLAGS_UNIXCOMMON) -lrt -ldl $(LDFLAGS_UNIXSDL) /opt/steamvr/bin/linuxarm64/libopenxr_loader.so -Wl,-rpath,/opt/steamvr/bin/linuxarm64 -lGL -lX11'
  • CFLAGS_SSE= and CFLAGS_SSE2= empty the -msse/-msse2 the makefile adds to the software rasteriser; the SSE code itself is guarded.
  • -std=gnu99: GCC 15 treats true/false as keywords and qtypes.h defines them.
  • The loader is linked by full path. With -lopenxr_loader the linker picked /usr/lib/libopenxr_loader.a, a 14 KB stub, because sdl2-config puts -L/usr/lib first, and every xr* symbol came back undefined.

Result: darkplaces-sdl, a 3.9 MB ARM64 binary linked to SDL2, libGL and SteamVR's loader.

Before this: the Proton dead end

The Windows x86-64 build was tried first as a sideloaded OpenXR shortcut (2026-10-06). The engine, graphics and audio ran; VR never attached. Proton's OpenXR bridge needs an x86-64 runtime inside the Steam Linux Runtime container, and pressure-vessel imports only SteamVR's ARM64 one (Failed to load OpenXR 1 runtime for x86_64-linux-gnu from /opt/steamvr/steamxr_linux64.json: Unable to open "/opt"). XR_RUNTIME_JSON and a symlinked active_runtime.x86_64.json did not help, and even then the OpenGL binding would have stopped it (why). That is Valve's to change; the native build sidesteps it.

  • clang 19: gcc cannot build the Zancle library it uses.

Three zink problems, in the order they were found

  1. Crash in the driver while compiling the world shader (a libgallium thread, right after link world|OIT 0; DITHER 0; MODE 1). The game's automatic "GL safe mode" then kicked in on the next start and drew nothing usable. Cause: bindless textures. QVR_GLSAFE_OFF=2 (a mask of the game's VR_GLSAFE_* features, added by the patch) turns only that off, and -noglsafe stops safe mode from switching itself on.
  2. Jittering menu and world, worse with head movement. SteamVR reads the eye images before zink has finished them. QVR_XR_SYNC=2 inserts a glFinish() before each xrReleaseSwapchainImage (1 is glFlush, which does not fix it; 0 is upstream behaviour).
  3. Black world at a full 72 Hz, menu fine, green hand pointers visible. Found by mirror screenshots with the headset awake (the mirror is a crop of the game's own eye texture): any bloom, even the Low preset's 0.08, paints the eye images black. vr_bloom 0. Not traced in vr_bloom.cpp yet; the Medium and higher presets and the menu's Bloom slider turn it back on.

Performance: the real cost, and the settings

With the headset worn, the eyes cost about 4.6 ms per megapixel plus 4.5 ms a frame: 39 ms at the recommended 1728x1728 per eye, 23 ms at 70%, 14 ms at 50%, 8–9 ms at about 650x650. Nothing else moved the number: retro mode, PBR, TAA, dynamic-light and map-light shadows and their filtering, specular, fog, tone mapping, the FSR upscaler, the hidden-area mask, float depth, single-pass stereo, particles, decals, the body, lightmaps, the sky, texture filtering, the desktop mirror and the graphics presets all measured within the noise of looking around. Overdraw is fine (the game's own fragment counter reports shaded/kept = 1.0). So the per-pixel shader is simply heavy for this GPU, and resolution is the only lever.

How it was measured, and the trap

A morning of unfocused tests said the cost was resolution-independent. It was not: with the headset asleep SteamVR sets shouldRender off, the game stops rendering the eyes and the profiler was timing the 1280x720 mirror window. Only tests with the headset worn count. The game's per-pass GPU timers are also meaningless on this tiler (the first scope absorbs the whole render pass); only frame totals were trusted. The tools, all in ~/PCVR/QuakeVR/:

  • q1_sweep.sh "name|cmds" ...: loads E1M1 with the profiler on and steps through cumulative console-command changes 500 frames apart; q1_report.sh prints GPU ms and fps before each step.
  • q1_profile.sh "cmds" "launch args" "ENV=val": one launch with cvars, arguments or environment (through env.test, sourced by the run script).
  • q1_shot.sh "name|cmds" ...: mirror screenshots per config, which is how bloom was caught.
  • q1_relaunch.sh: sets QVR_EXTRA in the run script and relaunches through Steam.

Why not Proton

SelacoVR ships as a Windows 64-bit zip. Under Proton Experimental (ARM64) the engine starts, finds the ipk3 and the mods, opens OpenAL, and then throws a C++ exception that ends in STATUS_NONCONTINUABLE_EXCEPTION about four seconds in, with +vr_mode 0 as much as in VR, so it is the engine under FEX, not the headset. Steam's own Selaco on the Frame is a native Linux build anyway, and the mod's source is public, so the native route was the obvious one.

Build

selaco_build.sh runs selaco_port.py (idempotent; it restores the files it rewrites from git first), then CMake/Ninja with -DENABLE_OPENVR=ON -DDYN_OPENVR=ON, system SDL2 and OpenAL, our ZMusic, and HAVE_VULKAN left on. The patches:

  • GCC 15 / C23: <cstdint> in ZWidget, <math.h> in thirdparty/math/sqrt.c, and -std=gnu89 for the lemon and re2c build tools (K&R-era C that C23 rejects).

Controls: three things SteamVR does with custom OpenXR bindings for Proton apps

  1. One interaction profile, or the custom file is ignored. SteamVR builds a Proton OpenXR app's input context from auto-generated defaults (~/.config/openvr/config/openxr/steam.app.<id>_<type>_N_binding.json, rewritten every launch) and only honours the user-selected Frame-path file when that context holds a single profile. This mod suggests Touch and Index; Quake II suggests only Touch, which is why its binding just worked. The launcher keeps the app's Index default unwritable (a read-only {}), so SteamVR logs "Unable to write" and loads one binding.
  2. Touch-typed files get auto-remapped. A custom file with controller_type: oculus_touch is treated as Touch paths and pushed through the Frame remap, which drives each hand's trigger and bumper from the one Touch trigger, so bumper and trigger can't differ. A file carrying a haptic entry for an action the app doesn't define ("Unknown action … when loading binding file") is dropped whole; keep "haptics": [].
  3. The mod's actions were hand-scoped. Jump and crouch accepted right-hand sources only, reload, flashlight, alt-fire and menu left-hand only, and under SteamVR the menu action was ignored in favour of a reload+crouch hold chord. That is in code, so the fix is a rebuild.

The OpenXR loader needs -DWINAPI_PARTITION_SYSTEM=0 under the project's -Werror=undef. The shader_compiler.exe steps fail (a Windows tool), which does not matter: the compiled shaders ship in alpinefaction.vpp.

Install and launch

The NSIS installer found the prefix's empty stub Steam folder instead of the real game, so its files were moved into steamapps/common/FarCry. Making it run

  1. Renderer crash. The DXVK fork's Wine debug logging corrupts a register in this MSVC build, so the Vulkan loader pointer turns into a module handle. DXVK_LOG_LEVEL=none avoids the logging path.
  2. HUD crash. Proton's 32-bit OpenVR bridge asserts on any overlay given a Vulkan texture (vroverlay_manual.c:465), and CryVR draws its HUD and menus that way. A 32-bit proxy openvr_api.dll (ovrshim, built on the Frame with clang and lld-link) intercepts that call. It copies the HUD off the GPU asynchronously, scaled to 1024 pixels, and only when it changes. The mod's own library sits beside it as openvr_api_real.dll.
  3. Getting pixels into SteamVR. SteamVR's raw-pixel overlay path stops for good after about 460 updates. Its from-file path shows only the first image per file name, and new names leak about 5 MB each in the compositor until SteamVR restarts. The fix is hudbridge, a native ARM64 OpenVR overlay app. ovrshim writes each frame into a shared file in /tmp, and hudbridge uploads it to its own Vulkan images and hands them over with SetOverlayTexture, the path native apps use. SteamVR won't let one process texture another's overlay, so hudbridge draws a mirror panel. It copies the game panel's position, size, visibility and curvature about 80 times a second and sits just above it. The game panel keeps one transparent pixel, so the laser pointer still clicks the menus. Memory stays flat, and the helper exits with the game.

Porting the engine

The engine's VR code sits in one folder and only a few places assume Android. The patch script swaps those for desktop equivalents:

  1. Graphics binding. The OpenGL ES and EGL session setup becomes desktop OpenGL with a GLX binding to SDL's X11 window, as in the Quake port. The engine requests OpenXR 1.0 (SteamVR's version) and creates the instance on first use, since there is no Android start-up hook.
  2. Renderer. VR forced the mobile GLES renderer; a failed load opens a blocking warning box. It now loads the desktop GL renderer. That renderer swaps the window once per eye, so the desktop swap is skipped.
  3. Menu panel. Menus are drawn on a curved cylinder layer, which SteamVR does not support. They now go on one flat quad of the same size and distance, shown to both eyes.
  4. A latent crash. The engine's model lookup read one entry past the end of its table. On Android the next value happened to be zero; here it was 2, and the client crashed on load.
  5. Small things. The Android haptics service is stubbed (controller rumble still works), GCC 15 needs -std=gnu17, the client needed its C++ headers ahead of its min/max macros, and the weapon calibration file moved from /sdcard into the game folder. Xiph's GitLab was down, so three audio libraries came from Xiph's GitHub mirrors at the same commits.

Building it

The build itself only needed one fix. CMake picked up the system's static OpenXR loader archive, which can't be linked here, so the renderer failed to load with missing xr* symbols. Fixes

  1. See-through menus. The menu panel was blended using the menu art's own alpha, and SteamVR honours it, so dark parts of the menus showed the world through them. The panel is opaque now.
  2. Multi-draw indirect. The renderer batches level geometry into indirect multi-draws. On the Frame's GPU driver that cost about 80 ms a frame (10–12 fps). Its existing fallback path takes 5 ms at full resolution, and both games now use it by default.
  3. Tiled rendering in Outcast. Outcast's busy scenes draw 300 to 1,800 models a frame. In the GPU's normal tiled mode each draw cost 40–50 µs, so the heaviest moments ran at 13–20 fps. Rendering straight to memory (TU_DEBUG=sysmem) brought the same scene from 48 ms to 11 ms. It slows Academy's levels from 5 to 12 ms, so it's a per-game default: on for Outcast, off for Academy.
  4. Not the problem: resolution, model detail, GPU skinning and the visual effects all made little or no difference. Every measurement was taken with the headset worn, from the game's own GPU timing.

Tribes 2 VR: the mod runs, but its menus can't fuse on the Frame

Bruhlitz's Tribes2VRmod (a QOL-24 test build uploaded 2026-10-09) is a 32-bit DLL injected into the free Tribes 2. Under Proton it did everything its log asks for: OpenVR up at 72 fps, every engine hook verified, legacy controller input alive, arm IK installed. Two things stopped it on this headset, one in TribesNext and one in how the mod presents 2D screens to wide, asymmetric lenses. Uninstalled the same day; documented for whoever tries next.

Mod
github.com/Bruhlitz/Tribes2VRmod, folder tribes2vr-QOL-24 (tribes2vr.dll, tribes2vr.ini, tribes2vr_launcher.exe), MinGW, OpenVR legacy input, OpenGL hooks on wglSwapBuffers + exe patches
Game
Tribes 2 25034 (free: tribes2gsi.exe from TribesNext, a Wise installer with no silent switch) + TribesNext RC2a
Tried
2026-10-23 in a shortcut-only Proton Experimental prefix; everything removed again, scripts kept

What worked

  • The mod needs openvr_api.dll (32-bit) next to it and doesn't ship one; the OpenVR SDK's bin/win32 copy works through Proton's vrclient.
  • Steam strips backslashes from shortcut launch options, so the launcher's C:\...\Tribes2.exe argument arrived as C:DynamixTribes2GameDataTribes2.exe. The wrapper appends the argument itself, and the launcher forwards extra arguments such as -nologin to the game.
  • The mod's byte-signature checks passed against the TribesNext RC2a-patched exe: camera, frustum, arm IK and Con::evaluate hooks all verified.

Blocker 1: TribesNext login

RC2a authenticates through a Ruby helper (rubyintersect.dll + msvcrt-ruby190.dll). Under FEX it page-faults inside the Ruby runtime, and the TribesNext scripts then report an unpatched exe, so no account login or creation. -nologin reaches the offline LAN/Training shell. The newer TribesNext 20250922 preview drops Ruby for native authentication and advertises Wine support; it was the untried next step for online play, with the caveat that the mod's signatures are tied to a specific exe.

Blocker 2: 2D screens on asymmetric lenses

In the shell the mod submits one identical image to both eyes at full texture bounds; its own log says so: "no eye crop available - submitting full bounds, image will double". The Frame's per-eye projections are wide and mirror-asymmetric (raw tangents l −1.65, r 1.22, t −1.73, b 1.17), so the same pixel lands at a different angle in each eye and the menus never fuse, with menuOverlay true or false. Two more of the mod's modes are ruled out here: its default crop mode (frustumMode 3) needs the game to draw a 144° vertical FOV to fill the lens ("VERTICAL IS SHORT … stretched 407% taller"), and depth stereo (stereoMode 2) needs readable depth that this engine never leaves behind under zink. frustumMode 2 (the headset's per-eye projection) with stereoMode 1 was configured for the 3D world but not tested before the decision to stop. Driving the menus through the SteamVR dashboard's desktop view would have been the workaround.

For the author

A 2D-screen path that crops each eye from the submitted image using GetProjectionRaw tangents (as the crop mode already does for 3D frames, but assuming the screen's own FOV instead of a game frustum), or that renders the screen quad per eye with the headset projection, would make the shell usable on wide-FOV headsets.
